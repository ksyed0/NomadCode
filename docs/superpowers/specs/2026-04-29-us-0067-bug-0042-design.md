# Design Spec: US-0067 (Monaco Custom Themes) + BUG-0042 (FileExplorer Ref Fix)

**Date:** 2026-04-29
**Branch:** `feature/us-0067-bug-0042`
**Stories:** US-0067 (EPIC-0005), BUG-0042
**Effort:** S (half-session)

---

## Overview

Two independent fixes shipped together: (1) register all 11 NomadCode themes with Monaco's `defineTheme` so editor syntax colours match the user's chosen theme, and (2) replace a boolean-prop trigger pattern in `FileExplorer` with `useImperativeHandle` to eliminate the `react-hooks/set-state-in-effect` lint violation.

---

## US-0067 — Monaco Custom Theme Registration

### Problem

`getMonacoTheme()` maps every ThemeId to `'vs'` or `'vs-dark'` because calling `editor.setTheme(themeId)` with an unregistered name causes Monaco to silently stay on its default. The user's chosen palette (Dracula, Nord, Solarized Light, etc.) is never applied to syntax tokens — only the light/dark mode distinction carries through.

### Design

**New file: `src/theme/monacoThemes.ts`**

Exports a single conversion function:

```ts
export function buildMonacoThemeData(t: ThemeTokens): IStandaloneThemeData
```

Maps `ThemeTokens` fields to Monaco's `IStandaloneThemeData` format:

| Monaco key | Source |
|---|---|
| `colors['editor.background']` | `t.bg` |
| `colors['editor.foreground']` | `t.text` |
| `colors['editor.selectionBackground']` | `t.bgHighlight` |
| `colors['editor.lineHighlightBackground']` | `t.bgElevated` |
| `colors['editorCursor.foreground']` | `t.accent` |
| `tokenColors` keyword rule | `t.keyword` |
| `tokenColors` string rule | `t.string` |
| `tokenColors` comment rule | `t.textMuted` |
| `tokenColors` number/type/function rule | `t.accent` |

All 11 themes are derived automatically from `THEMES` — no hardcoded colour values in this file. `base` is `'vs-dark'` for dark themes, `'vs'` for light themes (Monaco requires a valid base).

**Changes to `src/utils/MonacoAssetManager.ts`**

`buildMonacoHtml` gains an injected block before `editor.create` that calls `monaco.editor.defineTheme(id, data)` for all 11 themes:

```js
// injected into Monaco HTML before editor.create
Object.entries(NOMAD_THEMES).forEach(([id, data]) => {
  monaco.editor.defineTheme(id, data);
});
```

`NOMAD_THEMES` is serialised from `buildMonacoThemeData` for each `ThemeId` at bundle-build time (evaluated in `MonacoAssetManager.ts`, not at runtime in the WebView).

`buildMonacoHtml` signature changes:
```ts
// before
buildMonacoHtml(vsBaseUrl: string, initialTheme: 'vs' | 'vs-dark', prettierSource?: string): string
// after
buildMonacoHtml(vsBaseUrl: string, initialTheme: ThemeId, prettierSource?: string): string
```

**Changes to `src/theme/tokens.ts`**

`getMonacoTheme` return type widens from `'vs' | 'vs-dark'` to `ThemeId` and returns `id` directly:

```ts
// before
export function getMonacoTheme(id: ThemeId): 'vs' | 'vs-dark' {
  return THEMES[id].mode === 'dark' ? 'vs-dark' : 'vs';
}
// after
export function getMonacoTheme(id: ThemeId): ThemeId {
  return id;
}
```

### Acceptance Criteria Coverage

- **AC-0202** — `defineTheme` called for all 11 ThemeIds on editor boot ✓
- **AC-0203** — `getMonacoTheme()` returns ThemeId (not `vs`/`vs-dark`) ✓
- **AC-0204** — `buildMonacoHtml` injects all `defineTheme` calls before `setTheme` ✓
- **AC-0205** — Theme switch sends `SET_THEME` with new ThemeId; Monaco applies within one frame ✓
- **AC-0206** — Unit tests verify each theme's payload has non-empty background, foreground, and keyword/string/comment token rules ✓

### Testing

New file: `tests/unit/monacoThemes.test.ts`

- For each of the 11 ThemeIds: `buildMonacoThemeData` returns non-empty `colors.background`, `colors.foreground`, and token rules for `keyword`, `string`, `comment`
- Dark themes produce `base: 'vs-dark'`; light themes produce `base: 'vs'`
- `getMonacoTheme` returns the ThemeId unchanged
- `buildMonacoHtml` HTML string contains `defineTheme` calls for all 11 themes

## BUG-0042 — FileExplorer Imperative Ref

### Problem

`FileExplorer` accepts `triggerNewFile?: boolean` and `onNewFileDismissed?: () => void` props. A `useEffect` watches `triggerNewFile` and calls `handleHeaderNewFile()` (which calls `setState`) inside the effect body — violating `react-hooks/set-state-in-effect`. The current workaround is an `// eslint-disable-next-line` comment on line 368.

### Design

Replace the boolean-prop trigger pattern with `useImperativeHandle`.

**Changes to `src/components/FileExplorer.tsx`**

Export a handle type:
```ts
export interface FileExplorerHandle {
  openNewFileDialog(): void;
}
```

Wrap the component with `forwardRef<FileExplorerHandle, FileExplorerProps>`. Inside `useImperativeHandle`:
```ts
useImperativeHandle(ref, () => ({
  openNewFileDialog: handleHeaderNewFile,
}), [handleHeaderNewFile]);
```

Remove props `triggerNewFile` and `onNewFileDismissed` from `FileExplorerProps`. Remove the offending `useEffect` (lines 366–372) and its eslint-disable comment entirely.

**Changes to `App.tsx`**

Replace:
```ts
const [triggerNewFile, setTriggerNewFile] = useState(false);
// ...
onNewFileDismissed={() => setTriggerNewFile(false)}
triggerNewFile={triggerNewFile}
// ... in command handler:
setTriggerNewFile(true);
```

With:
```ts
const fileExplorerRef = useRef<FileExplorerHandle>(null);
// ...
ref={fileExplorerRef}
// ... in command handler (synchronous, no state flip):
fileExplorerRef.current?.openNewFileDialog();
```

### Testing

- `FileExplorer.test.tsx` — update tests to use `createRef<FileExplorerHandle>()`, call `ref.current.openNewFileDialog()`, verify modal appears
- `App.test.tsx` — verify "File: New File" palette command calls `openNewFileDialog` via spy on the ref method; verify `triggerNewFile` state no longer exists in component
